# ADR-0015：平台邀请码池与随机邀请码

## 背景

NewAPI 中转站的邀请链接形如 `https://站点?aff=<邀请码>`。运营者希望：

1. 主页（公开目录）展示的邀请码能**自动轮换**，而不是永远只有一个；
2. 用户各自站点上填的邀请码能被平台复用，不用管理员再抄一遍；
3. 管理员能直接补充邀请码（比如运营者自己的码）；
4. 留空邀请码的行为可配置。

## 决策

引入**平台邀请码池**（`invite_codes` 表）+ 站点级 `RANDOM` 哨兵值。

### 池子的两个来源（自动合并）

| 来源 | 说明 |
|---|---|
| `user` | 用户在自己站点上填写的 `aff_code`。**无需额外写入**——池子查询时直接并入，用户填了码就等于入池。 |
| `admin` | 管理员在「系统设置 → 邀请码池」手动登记的码，可写备注。 |

同一个码两边都有时去重，并以 `admin` 记录为准（标签更权威）。

### 站点侧的两种表达

| `aff_code` | 行为 |
|---|---|
| 具体码（如 `dl7w`） | 固定使用该码，不参与随机。 |
| `RANDOM` | 每次展示时从池中抽取。大小写不敏感，`RANDOM` 本身永不作为邀请码。 |
| 留空 | 由系统设置 `aff_blank_policy` 决定：`none` 不带码 / `random` 等同 `RANDOM`。 |

### 主页 vs 个人页（关键区别）

- **主页 `/` 与站点详情页**：公开目录，展示时从池中**随机抽取**（`usePool: true`）。
- **个人分享页 `/p/<slug>`**：站点主人自己的页面，**始终展示他自己的码**，不参与平台随机（`usePool: false`）。把自己的页面变成别人的推广位是错的。

抽取以「页」为单位播种（主页按小时、详情页按 provider id），因此**同一次渲染里指向同一站点的多个条目展示同一个码**（页面自洽），而不同时间/不同页面之间会变化（这才是随机的意义）。

### 池子按站点隔离

邀请码只在其所属中转站有效，因此池子始终以 `normalized_base_url` 为作用域查询，绝不可能把 A 站的码拼到 B 站链接上。

## 后果

- 池子**自增长**：用户填码即入池，无需管理员干预。
- 池子为空时（或该站点无可用码）退化为**不带码的普通链接**，不会生成坏链接。
- `RANDOM` 是保留值：校验层拒绝把 `RANDOM` 登记为邀请码，避免自我指涉。
- 个人页的行为与主页不同，属于有意设计，已由测试固定。
- 迁移 0005 为增量建表；`invite_codes` 已纳入整库导出/导入（ADR-0014），换服务器时池子一并带走。

## 验证

- `tests/inviteCode.test.ts`（11 项）：两源合并与去重、`RANDOM` 永不入池、站点隔离、`addCode` 幂等与保留值拒绝、空池返回 null、同种子确定 / 跨种子分散、`listPools` 分组、删除只删管理员登记行。
- `tests/inviteResolution.test.ts`（8 项）：policy=random 时主页抽到用户码、policy=none 时不带码、显式 `RANDOM` 在 policy=none 下仍抽、固定码优先于池、池空时退化、**个人页只用主人自己的码**、个人页无码时不抽、详情页参与抽取。
